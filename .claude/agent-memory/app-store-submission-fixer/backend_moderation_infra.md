Before building "new" account-deletion or moderation backend for a rejection, check what already exists — as of 2026-07-01 the live Supabase project (wtncuzcskpigqpmnxwws) already had:

- `delete_my_account()` RPC (SECURITY DEFINER) — existed but only ran `delete from auth.users`, relying on ON DELETE CASCADE. **Bug found & fixed**: several tables have NOT NULL / ON DELETE NO ACTION or RESTRICT FKs to auth.users on `created_by`/`approved_by`/etc. columns (`meetup_invites`, `meetup_link_tokens`, `squad_link_tokens`, `game_link_tokens`, `user_freezes`, `blackouts`, `venue_bookings`, plus nullable ones on `role_grants`, `profile_verifications`, `point_ledger`, `venue_submissions`). Any user who ever created one of those rows would hit a FK violation and deletion would silently fail. Fixed via migration `fix_delete_my_account_full_cleanup` (nulls the nullable ones, deletes the NOT-NULL-FK rows, deletes `storage.objects` owned by the user, then deletes the auth user). **When touching delete_my_account again, re-check `pg_constraint where confrelid = auth.users` for new NOT-NULL restrictive FKs added since — they can silently break the RPC.**
- `user_blocks` table + `rpc_block_user(p_peer uuid)` / `rpc_unblock_user(p_peer uuid)` / `is_blocked(a,b)` — fully wired end-to-end in Flutter (`lib/data/repositories/block_repository_impl.dart`, `lib/features/social/block_providers.dart`, used in `user_profile_screen.dart`). Note: there is ALSO a dead/legacy `rpc_block_user(p_peer uuid, p_block boolean)` overload writing to a separate `restrictions` table — Flutter never calls this 2-arg overload (confirmed via grep), so `user_blocks` is the true source of truth. Don't "fix" the `restrictions` path without checking who uses it first.
- `moderation_reports` table + `report_content(...)` RPC — fully wired via `lib/services/moderation_service.dart` and `lib/features/moderation/presentation/widgets/report_dialog.dart`, but **only reachable from `user_profile_screen.dart` (reporting a user)** — posts in the feed had NO report control until this session added one to `lib/features/social/presentation/widgets/feed_post_card.dart` (an overflow "more" icon at the end of the like/comment/repost action row, opening a bottom sheet with Report + Block).
- Admin-side moderation UI already exists: `lib/features/admin/presentation/screens/moderation_queue_screen.dart`, plus an `app_admins` table (just `user_id`).
- **Feed blocking gap (fixed 2026-07-01)**: neither `get_home_feed(p_limit, p_cursor)` (the one Flutter's `feed_notifier.dart` actually calls) nor `get_feed(p_limit, p_offset)` ever filtered out blocked users' content. Fixed via migrations `filter_blocked_users_from_get_home_feed_cursor` and `filter_blocked_users_from_get_feed`. Note: `get_home_feed(p_limit, p_offset)` (a separate jsonb-returning overload) was found to be pre-existing dead/broken code (references a `post_reposts.original_post_id` column that no longer exists) and unused by the client — deliberately left unfixed/untouched, out of scope.
- Reporting/blocking a user did not notify the developer team at all. Fixed by reusing the *existing* notifications+push pipeline (`public.notifications` table already has a generic `trg_push_on_notification_insert` AFTER INSERT trigger) rather than adding Resend/email — no Resend API key exists in Vault (`vault.secrets` only had `push_trigger_secret`, `supabase_anon_key`), so email-based notification wasn't feasible without new user-provided secrets. New triggers `trg_notify_admins_of_report` (moderation_reports) and `trg_notify_admins_of_block` (user_blocks) fan out a notification to every row in `app_admins`. New notification_kinds: `moderation.report_submitted` (high/inapp+push), `moderation.user_blocked` (low/inapp). EXECUTE on both new trigger functions was revoked from anon/authenticated (matches project's existing `p2_revoke_execute_internal_functions` hardening convention) since they're trigger-only, not meant to be called directly via PostgREST.
- No local `supabase/migrations/*.sql` files exist in the repo — schema history lives only server-side (checked via `list_migrations` MCP tool). Migrations must be applied directly via `mcp__supabase__apply_migration`; there's no local file to also update.
